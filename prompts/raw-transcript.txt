  Mongo

  - API layer (app/api/orders.py): thin. Routes only route and map errors — e.g.
  get_order (orders.py:14-19) catches orders_service.OrderNotFound and raises
  HTTPException(404). No logic.
  - Service layer (app/services/orders.py): business rules, HTTP-free. get_order
  (services/orders.py:11-15) fetches via the repo and raises the domain
  exception OrderNotFound (services/orders.py:7-8); list_orders maps docs to
  Order models.
  - Repository layer (app/repositories/orders.py): the only code that touches
  Mongo. get/list_recent call get_db()[ORDERS] and _to_order_dict
  (repositories/orders.py:6-9) translates Mongo's _id back to order_id.
  - DB layer (app/db.py): get_client (db.py:17-26) lazily constructs either an

  Existing endpoints (confirmed, all read-only): GET /health, GET /orders, GET 
  /orders/{order_id}. The two mutating endpoints in the brief — POST 
  /orders/{order_id}/apply-discount and POST /webhooks/payment — do not exist

  6. Risks

  Duplicate payment webhooks (confirmed risk). deliveries() always fires twice
  (gateway.py:62-66) and fixtures.json webhook_1 has times_delivered: 2. Without
  idempotency the order could be marked paid twice / a payment recorded twice.
  Mitigation: dedupe on payment_id — e.g. a unique-indexed payments record or a
  conditional update (update_one filtered on status != "paid"), so the second
  delivery is a no-op.

  Concurrent discount application (confirmed-as-tested). fixtures.json apply_4
  sends two codes to ord_c_3005 "at_the_same_time" and apply_5 sends two
  "one_after_another" to ord_c_3004. A naive read-modify-write can double-apply
  or lose an update. Mitigation: an atomic conditional update (apply only if no
  discount present) or a transaction — but note the mongomock caveat.

  Monetary precision (confirmed constraint, unspecified rule). All money is
  integer paise; create_payment rejects floats (gateway.py:41). A
  percent_off_bps × subtotal computation produces fractions of a paise — the
  rounding rule is deliberately unspecified (README §"Two things"). Compute with
  integer math (subtotal * bps // 10000, then min(cap_paise, …)), pick a
  rounding direction, and document it. SUPER60 (6000 bps, cap_paise: 4000) is a
  seeded case where the cap binds — a good test.

  Settlement accuracy (confirmed design requirement). Partners settle monthly on
  their share, and a partner's split ratio can change next month (README §5).
  Risk: storing only a code reference and recomputing at settlement time would
  use next month's ratio and mis-settle. Mitigation: snapshot
  partner_share_bps/rayy_share_bps and the discount amount onto the order at 
  apply time, so the monthly query reads the historical split, not the current
  code config. The split can't be derived later because discount_codes is
  mutable config loaded from JSON.

  Secondary (confirmed): expires_at is relative (discount_codes.py:26, PAST30
  has expires_in_days: -1) — an expired code must be rejected. status is an
  unconstrained string (models.py:22) — be consistent ("pending"/"paid").
  Verifying the signature requires the raw bytes (await request.body()), not a
  re-serialized model.

  Assumption: the webhook should also validate amount_paise equals the order's
  payable total before marking paid; the brief implies it ("production payment
  path") but no code asserts it.

  7. mongomock transaction caveat

  Confirmed. make test uses mongomock, which does not support transactions
  (README; db.py:20-24). If you solve concurrency/idempotency with
  multi-document transactions, they only run under make test-mongo/compose — and
  the README asks you to note that in NOTES.md. Prefer single-document atomic
  updates (update_one with a filter condition) where possible, since those work
  under both.

  - Expected behaviour — [I/D] — amount_paise is documented as "what the
  customer was actually charged" (gateway.py:17). Production path implies
  verifying it equals the order's payable total_paise. Not asserted in code, so
  the rule and the response are a design decision.
  - Relevant data — webhook amount_paise vs order total_paise (post-discount).
  - Validation — amount_paise == order.total_paise.
  - Failure cases — underpayment/overpayment; stale amount (webhook arrived
  before a discount was applied — note webhook_2 is explicitly ordered after: 
  [apply_2]).
  - HTTP — [D] 409/422 on mismatch, or accept-and-flag. Recommend reject (409),
  don't mark paid.
  - Test — signed webhook with wrong amount_paise → rejected, order stays
  pending.

  B5. Payment failures and retries  ⭐

  - Expected behaviour — the stub only models payment.succeeded (S,
  gateway.py:51-52); there is no payment.failed event server-side. "Payment
  failure + retry" is primarily a client requirement: on onPay rejection show an
  error (role="alert" in React / text "Payment failed" in Flutter) and
  re-enable the button (client/web/src/OrderSummary.tsx:10-12,
  client/flutter/lib/order_summary.dart:14-17). [S] on the client; [D/I] whether
  the server handles any non-success event (likely out of scope).
  - Relevant data — order.status ("paid" locks the button; "pending" allows
  retry).
  - Validation (client) — button disabled while pending (still reads "Pay");
  reads "Paid" & disabled only when status === "paid".
  - Failure cases — retry after a failure must not be blocked; a successful
  retry still must be idempotent server-side (B3).
  - HTTP — n/a (client).
  - Test — client test: onPay rejects → alert shown, button re-enabled; second
  attempt allowed.

  B6. Order already paid  ⭐

  - Expected behaviour — a webhook for an already-paid order (new or duplicate
  payment_id) must not re-apply. [S] via the idempotency requirement; overlaps
  B3. [D] whether a different payment_id on a paid order is an error or a benign
  no-op.
  - Validation — status guard in the conditional update (status != "paid").
  - Failure/HTTP — duplicate payment_id → 200 no-op; conflicting new payment on
  paid order → [D] 200 ignore vs 409.
  - Test — pre-set ord_x to paid, deliver a webhook → no change; assert single
  payment of record.

  B7. Unknown order in webhook

  - Expected behaviour — [D] — webhook references a nonexistent order_id. Ack
  200 (stop retries for an un-actionable event) vs 404/422.
  - Validation — order lookup returns None.
  - HTTP — [D]; recommend 404 for a clearly bad reference (or 200-ack if you
  prefer not to leak existence). Document the choice.
  - Test — signed webhook with order_id: "ord_missing" → chosen status, no

  B8. Concurrent webhook deliveries  ⭐

  - Expected behaviour — two near-simultaneous deliveries of the same payment_id
  (the real gateway sends "sometimes seconds apart", gateway.py:22) must still

  check-then-write is not.
  - HTTP — both 200.
  - Test — fire webhook_1's two deliveries concurrently; assert exactly one
  payment.

  Issues found

  All are low-severity robustness gaps, none blocking. Explaining before any fix
  (and I've changed nothing yet):

  1. Validly-signed malformed webhook body → 500, not 400.
  payments.process_webhook does json.loads(raw_body) and
  body["order_id"]/["amount_paise"]/["payment_id"] after the signature check. A
  signed-but-malformed or key-missing body raises JSONDecodeError/KeyError →
  unhandled 500. Only reachable by someone holding the webhook secret (signature
  is verified first), so real-world risk is low, but a 400 would be cleaner
  than a 500.
  2. Float amount_paise would bypass the integer-money rule. The handler
  compares body["amount_paise"] != order["total_paise"]. If a sender passed
  45900.0, Python's 45900.0 == 45900 is True, so it'd pass and be stored as a
  float in payment. The gateway's create_payment rejects non-ints at source
  (gateway.py:41), so this can't happen via the real path — but there's no
  explicit isinstance(..., int) guard at the webhook boundary, unlike elsewhere
  in the codebase.
  3. event field is not validated. The handler never checks body["event"] == 
  "payment.succeeded". The stub only emits that event, so it's moot today, but
  any future event type would still mark the order paid.
  4. Minor: 409 message precision. If an order is paid in the race window
  between apply_discount's read and the atomic set_discount, the guard correctly
  rejects with 409 but the detail reads "discount already applied" rather than
  "order already paid". Correct status, slightly imprecise message. Not worth
  special-casing.

  No genuine race conditions found. Both write paths are guarded by
  single-document atomic conditional updates (modified_count), which are atomic
  in real MongoDB and effectively atomic under mongomock's single-threaded
  model. The check-then-update TOCTOU in both services is backstopped by the
  DB-level filter, so interleaving cannot double-apply or double-pay.

     % avoids fractional rounding).

     prefix.replace(/\B(?=(\d{2})+(?!\d))/g, ",").
     - `₹${sign}${grouped}.${String(rem).padStart(2, "0")}`.
